## Authority boundary

Remote model execution is governed disclosure and cost, not authority-free inference. Runtime may propose one bounded invocation, but only Protected Root may validate the exact persisted workflow/context/provider state and issue durable authority. Runtime receives opaque secret-handle identifiers, never raw credentials. The isolated provider runner resolves a handle only for the exact active permit, provider connection, credential slot, and expiry.

The schema-59 permit kernel and deterministic in-process gateway do not send network traffic. The isolated provider runner exercises one real OpenAI-compatible Responses HTTP route. Fresh and resumed compatibility-agent turns under Root ownership now execute only through a lease-scoped Root dispatcher and that isolated runner; a missing dispatcher refuses the call instead of falling back to the legacy provider registry. Other provider surfaces remain compatibility foundations until separately migrated.

ChatGPT browser/device OAuth uses the same governed route. The execution permit contains only access and identity-token handles; the renewable refresh token remains exclusively behind Root-owned authentication/rotation. Root holds the connection rotation gate until a buffered call completes or a returned stream completes or is dropped. The isolated runner cannot refresh, cannot read the refresh slot, cannot substitute the subscription route onto API billing, and performs exactly one physical attempt.

## Implemented deterministic gateway checkpoint

- Protected Root exposes one `GovernedModelProviderGateway` boundary that receives the complete secret-free authorization receipt plus the exact request; Runtime never receives raw provider credentials.
- Provider requests use a separately versioned exact JSON wire artifact with SHA-256 domain separation and explicit rejection of non-finite sampling values and payloads above 16 MiB. The canonical contract codec remains strict and unchanged.
- Root recomputes the exact request artifact and checks invocation, permit, Runtime identity, route/model, client request identity, output limit, permit time, and workflow lease immediately before planning and dispatch.
- The immutable `InvocationManifest` and `Planned` `ModelRun` are durable before the run becomes `Dispatched`; the stable client request identity is retained without prompt content.
- Response acceptance revalidates the exact current permit, workflow revision/generation/owner/lease, provider catalog, response contract/model/identity, token usage, and response-size bound.
- Completed runs retain content-addressed response metadata and bounded integer usage only. Raw provider output and arbitrary provider metadata are returned in memory but are not persisted in generic Runtime response storage.
- Runner failures are classified by provider-contact evidence. A proved pre-contact failure settles the dispatched run `Failed`; only a transient pre-contact failure may start one new independently authorized invocation. Delivery, timeout, malformed output, child-process loss, provider error, invalid response, and results arriving after workflow reassignment or revision change settle conservatively as `OutcomeUnknown` and are never automatically retried.
- While a dispatched non-streaming gateway call is in flight, Root polls the exact persisted invocation permit, workflow revision, lease generation/owner, and expiry. Typed workflow cancellation, reassignment, lease expiry, or any inability to prove current authority drops the gateway future. The isolated runner's kill-on-drop process supervision then terminates and reaps its complete process tree.
- Because cancellation can occur after network contact or billing, Root settles that physical `ModelRun` as `OutcomeUnknown`, never `Failed` or `NoEffect`, and never retries it. The cancelled future cannot return a late response into validation or commit.
- A deterministic fake gateway proves exact one-call dispatch. Request/model substitution is rejected before the gateway is called, and a post-dispatch workflow revision change rejects the response and preserves `OutcomeUnknown` evidence.

## Implemented isolated provider-runner checkpoint

- `mcg-provider-runner` is a fixed adjacent one-request child with a bounded 16 MiB request/response protocol. Protected Root accepts only a regular non-link executable, pins its SHA-256 identity at client construction, revalidates the bytes immediately before every launch, and refuses substitution. It launches with a cleared environment, kill-on-drop supervision, Windows Job Object or POSIX process-group containment, concurrent bounded stdout/stderr drains, and a single deadline.
- The child independently recomputes the complete proposal, disclosure, request, and permit hashes and validates the invocation, role, attempt revision, lease generation, Runtime actor and identity, TaskContract, route, provider, model, destination, limits, expiry, permit, and exact handle map before credential or network access.
- The Root-to-runner request contains only opaque connection/credential-slot bindings. The child loads only exact operating-system credentials, refuses credential mutation, and zeroizes transient `ProviderCredential` material on drop and process exit. API-key, bearer-token, credential-free, and exact access-plus-identity ChatGPT OAuth routes are supported; OAuth refresh authority remains Root-only.
- The provider client is configured for exactly one physical attempt. Any later retry must receive a distinct invocation, permit, and `ModelRun`; the child cannot create a hidden physical retry.
- Root permits at most two physical attempts for one logical compatibility request. The second exists only after durable `Failed` evidence proves no provider contact, and receives a fresh invocation ID, permit ID, client request ID, and `ModelRun`. Both contexts retain the same logical request ID/hash, ordinal, ceiling, and exact `retry_of_invocation_id`. Final pre-contact denial stops after one attempt; any possible-contact outcome stops as `OutcomeUnknown`.
- Provider failures cross the pipe only as categorical codes. Raw provider error bodies, messages, credentials, prompts, and arbitrary metadata are not returned as diagnostics or persisted by the runner.
- A real-process loopback test exercises the OpenAI-compatible `/v1/responses` route through the fixed child. A separate credential test proves the API key is absent from the Root request, appears only in the outbound authorization header, and never enters the response artifact. A cancellation test waits for confirmed provider contact, drops the in-flight client future, and proves the supervised child shutdown closes or resets the provider transport within a bounded deadline.
- Packaging contracts include and qualify the runner for Windows installer/portable, Linux Debian/AppImage, and macOS payloads. Native installed-package execution remains part of the open Stage 6 exit gate.

## Implemented production compatibility-agent route

- Protected Root installs one non-replaceable dispatcher when it acquires authoritative ownership. Runtime gives it only the selected provider/model request and exact live `AgentLeaseId`; Root reloads provider/catalog state and chooses the fixed adjacent isolated runner.
- Fresh turns and approval resumptions both use a lease-scoped gateway. Under Root ownership, absence of the dispatcher fails closed before registry or OAuth fallback; embedded pre-Root test/runtime use remains backward compatible.
- One transaction creates or reloads the immutable schema-60 attachment, verifies the current compatibility task/run/plan/instance/lease chain, and claims the Ready canonical attempt. Same-owner live replay is safe; expired, completed, reassigned, foreign-owner, or otherwise stale authority is rejected without changing the canonical attempt.
- Each physical call has a new invocation ID, stable client request ID, Root permit, and `ModelRun`. Input/output/cost/time limits are derived from the persisted lease, current model descriptor, and a hard per-call cost ceiling; the ContextManifest exposes only the immutable source reference and request-bound influence hashes.
- A bounded Root retry reclaims and revalidates current canonical authority before constructing the next physical attempt. It cannot redispatch the first invocation or reuse its permit/run identities, exceed two attempts, retry an explicit denial, or retry a failure for which provider contact or billing is possible.
- During each dispatched non-streaming call, Root continuously revalidates the exact active authorization. Typed workflow cancellation or stale authority stops waiting, tears down the isolated child through kill-on-drop supervision, records the attempt `OutcomeUnknown`, and fences all late output without creating a retry.
- The exact request, manifest, permit, plan, dispatch, and bounded response evidence use the existing Stage 6 result fences. No raw provider response, arbitrary metadata, or credential is added to generic durable state.
- Production streaming uses a distinct domain-separated request artifact, fresh invocation/permit/client-request/`ModelRun` authority, and the same lease-scoped Root dispatcher. Intermediate events are bounded and provisional; only a correlated completed response plus a valid runner terminal/exit can settle the run `Completed`. Cancellation, authority loss, stream error/end, or consumer drop tears down the isolated child and settles possible contact `OutcomeUnknown`; no exposed stream is retried. OAuth-backed calls use the same governed stream while Root holds the credential-rotation gate through completion or drop.
- A successful buffered or streaming completion stores one content-minimized observed-model fingerprint on the immutable completed `ModelRun`. Root binds the exact authorized provider/model, request hash, policy hash, returned model identity, and SHA-256 hashes of an allow-list of reported revision fields. Response content, response IDs, unknown metadata, and plaintext reported revisions do not enter the evidence. Failed, cancelled, and `OutcomeUnknown` runs cannot acquire a fingerprint. Legacy JSON without the optional field keeps its canonical representation and remains readable.
- Every new terminal governed provider run stores exact elapsed milliseconds and categorical settlement evidence. Completed runs store either a known integer micro-USD cost with the exact normalized authorized catalog-model source or an explicit unknown cost; proved pre-contact failures store zero with `NoProviderContact`; possible-contact failures retain unknown cost and `OutcomeUnknown`. Known cost above the exact permit ceiling fails closed and is never committed as completed.
- Catalog model identity now canonicalizes price rates as stable finite nonnegative decimal strings before hashing. Price-less descriptors retain their exact legacy hash; priced descriptors become permit-bindable without admitting canonical floating-point values. Provider configuration/catalog events retain only content-minimized model `SourceRef` receipts while the authoritative tables retain the complete catalog.
- Human `mcg invocation show` output prints the observed identity when present. Advanced shows a shortened identity beside the request/response evidence, Developer exposes the exact canonical value, and Simple exposes neither; all three read the same Root reconstruction record.
- Human `mcg invocation show` also prints latency, exact micro-USD cost or `unknown`, and the categorical terminal error. Advanced renders bounded latency/cost/error summaries, Developer exposes the complete canonical outcome evidence, and Simple remains unchanged.
- Compatibility waiting, completion, and failure now share the legacy settlement transaction with the attached canonical attempt. Approval waiting becomes `Waiting(Approval)` and clears worker authority; approved resume records `Waiting(Approval) -> Ready -> Running` and increments the lease generation; completed Work becomes `Verifying` without claiming success; terminal turn errors and denied/cancelled approvals become `Failed`. A stale or expired canonical generation rejects and rolls back the legacy settlement.

## Implemented independent compatibility Verify closure

- Runtime freezes one stable evaluation ID and timestamp in a durable `Verifying` checkpoint, persists the immutable objective report, and cannot settle an attached Work target without one Root-produced completion.
- Protected Root accepts only that evaluation ID. It reloads and validates the exact current prepared report, canonical attempt, TaskContract, planned `SuccessCondition` values, completed Work invocations, artifacts, and final Work response hash from authoritative storage.
- Root launches the fixed authenticated Runtime worker under a fresh durable generation and dispatches a distinct deterministic Verify invocation. Its context contains the immutable report reference; every criterion maps to the exact TaskContract clause and objective result. Missing or substituted evidence fails closed.
- Root constructs the CompletionCertificate from the completed Work and Verify lineage. Certificate persistence, canonical terminal transition, legacy task/run settlement, and evaluation-checkpoint completion occur in one SQLite transaction. An injected late legacy-projection failure leaves the workflow `Verifying` and persists no certificate.
- A crash after observational Verify but before settlement may repeat Verify under a new worker/invocation identity. Both immutable runs remain inspectable, no external effect is repeated, and the same prepared report and Work evidence produce identical criterion results.

## Implemented Tool/Skill/Capability contract and persistence kernel

- Stable `ToolManifest` v1 binds identity/version/hash, runner, input/output schemas, maximum effect, exact filesystem/network/secret/process capabilities, resource ceilings, seven-dimensional sandbox requirements, supported platforms, receipt semantics, and optional reconciler.
- Stable `SkillManifest` v1 binds input/output contracts, preconditions, exact Tool revisions, implementation, verification, tested conditions, exclusions, fallback, rollback, provenance, and lifecycle status. A Skill remains a validated procedure and never grants ambient execution authority.
- `CapabilityProfile` v1 is explicitly rebuildable selection evidence over Skills, Tools, probes, roles, model routes, coordination policies, and Runtime extensions. It carries bounded performance estimates but is not canonical authority.
- `SandboxCapabilityProfile` reports `Unavailable`, `BestEffort`, or `Hard` independently for filesystem, network, process-tree, secrets, environment, resources, and protected paths. Root compares every dimension and fails closed if any required guarantee exceeds the host.
- `ToolInvocationProposal` and `ToolInvocationPermit` bind the action, workflow revision/generation, authenticated Runtime identity, TaskContract, exact Tool manifest, immutable argument artifact/hash, effect, capabilities, resource limits, exact execution platform, sandbox profile, Root policy, expiry, and opaque secret handles.
- The deterministic Protected Root kernel rejects manifest/hash/Runtime substitution, an unlisted manifest, unsupported host platform, effect or resource overscope, capability drift, insufficient sandbox guarantees, and overlong/expired authority. Registration and the derived capability index are never treated as permits.
- Schema 61 stores immutable monotonic Tool and Skill manifest revisions/heads, a replaceable non-authoritative Capability Profile projection, immutable Tool proposals/permits, and exact permit-to-secret-slot handle bindings. Update/delete triggers protect durable authority while canonical reload verifies every embedded hash and denormalized identity, version, argument, proposal, issuance, and expiry column.
- Skill registration resolves every exact Tool revision/hash. Exact historical manifest replay is idempotent only while a consistent durable head remains; skipped revisions, substituted content, missing Tool dependencies, and damaged heads fail closed.
- Protected Root now verifies the exact registered manifest before intersection, issues and persists one proposal/permit/opaque-handle receipt through the Root-owned Runtime storage bridge, returns the original active receipt on exact replay, and refuses policy, manifest, host, Runtime, or proposal substitution.
- Historical authorization remains inspectable after workflow advance or permit expiry, but active execution and opaque-handle resolution independently require the exact current Running attempt revision, lease generation/owner, TaskContract, action envelope, and permit time window.
- Action-runner protocol v2 is the first migrated physical Tool executor. Protected Root derives a deterministic manifest from the exact executable SHA-256, platform, absolute capability root, read/write scope, sandbox declaration, and resource ceiling; registers it; persists the exact action/workflow/Root-adapter proposal and permit before dispatch; and sends the immutable envelope plus complete authorization bundle to the fixed child.
- The child independently recomputes manifest/proposal/policy/permit hashes, validates permit time and platform, re-hashes its own executable, checks the exact root/access/operation or reconciler mode, rejects network/secret/process authority, and opens the capability root only after every binding agrees. The parent also re-hashes the fixed executable immediately before launch, so replacement after initial measurement fails before possible effect.
- Filesystem create/read/inspect/compensate and reconciliation now consume the exact schema-61 authority. Other legacy executor families and progressive capability inspection remain open.
